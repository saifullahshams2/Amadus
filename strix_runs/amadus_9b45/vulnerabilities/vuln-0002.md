## Description

`composer.lock` pins `symfony/http-foundation` **v8.1.9**, covered by CVE-2026-118514: `RequestMatcher`/`MethodRequestMatcher` compared the request method verbatim, so security rules scoped to GET could be bypassed with a HEAD request (incomplete fix of CVE-2026-45075). Fixed in v8.1.11 (also 5.4.56 / 6.4.50 / 7.4.23). Transitive dependency of the direct `laravel/framework` v13.38.0.

## Evidence

**Advisory evidence:** `CVE-2026-118514` applies to `symfony/http-foundation` at installed version `v8.1.9`. The advisory is fixed in `8.1.11`.

**Transitive dependency:** introduced by the direct dependency `laravel/framework@v13.38.0`.

**Dependency chain:** `laravel/framework@v13.38.0 > symfony/http-foundation@v8.1.9`

**Usage analysis:** not imported by application code. Affected-symbol check: `rg -l 'RequestMatcher'` across `app/`, `config/`, `routes/`, `resources/`, `tests/` returns no hits, and no Symfony security configuration (packages/security.yaml, firewall/access_control definitions) exists in the repository — this is a Laravel app that uses `Illuminate` middleware exclusively (`EnsureUserIsInstructor` role check at app/Http/Middleware/EnsureUserIsInstructor.php:20-37, `auth` middleware groups in routes/web.php:45-54). The vulnerable class is only instantiated by Symfony Security's access_control/firewall machinery, which is absent. There is no source → sink path because the sink (method-scoped RequestMatcher rule) is never constructed. `not_imported` here refers to the affected symbol's usage, not the package (the package itself is loaded by Laravel on every request). This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

In the abstract, method-scoped security rules (Symfony security access_control with a `methods` option) can be bypassed by sending HEAD instead of GET, reaching controller side effects without a response body. In this Laravel application no Symfony security RequestMatchers exist and authorization is enforced by Laravel middleware/role checks inside controllers, so the bypass has no target and the vulnerable path is not reachable.

## Contextual CVSS

symfony/http-foundation v8.1.9 is imported transitively by laravel/framework v13.38.0 and handles every HTTP request at runtime, so the package is fully live. The vulnerable API is `Symfony\Component\HttpFoundation\RequestMatcher` / `RequestMatcher\MethodRequestMatcher` used inside Symfony security `access_control`/firewall rules with a `methods` option — a Symfony Security-layer feature. This application uses Laravel middleware for authorization (`EnsureUserIsInstructor` at app/Http/Middleware/EnsureUserIsInstructor.php, route middleware in routes/web.php) and defines zero RequestMatchers (`rg -l 'RequestMatcher' app/ config/ routes/ resources/` → no hits; no Symfony security config exists in the repo). With no method-scoped RequestMatcher rules, a HEAD request cannot bypass any control, so contextual impact is N/N/N; AC:H reflects the missing precondition (method-scoped matcher rule) that this deployment never creates.

## Remediation

Run `composer update symfony/http-foundation` (or bump laravel/framework to a release resolving http-foundation >= 8.1.11). No application change required; no method-scoped matcher rules exist to be bypassed.
