# Any instructor can delete any office's scenario and cascade-delete its student submissions

**ID:** vuln-0007
**Severity:** LOW
**Found:** 2026-11-08 16:54:15 UTC
**Target:** http://127.0.0.1:8088
**Endpoint:** DELETE /api/instructor/scenarios/{id}
**Method:** DELETE
**CWE:** CWE-639
**CVSS:** 2.7
**Confidence:** High
**Fix Effort:** Low

## Description

Any instructor can delete any scenario in the database regardless of which office created it, and the deletion cascades to every student's graded submissions for that scenario. Scenario deletion has an instructor role check but no ownership or office check, unlike every other instructor object operation in the application.

## Evidence

Exchange 240: instructor `mharper` (office LON1A0980) created scenario `zz-xcheck-3523` (201). Exchange 244: cadet of the same office submitted against it (200, score 100). Exchange 245: a cadet's DELETE was rejected 403 `Forbidden. Instructor access required.` Exchange 246: an instructor of a different office (XOFF22) issued the same DELETE and received 200 `Scenario 'zz-xcheck-3523' deleted successfully.` Database check after: 0 submissions remain for that scenario id (cascade confirmed). Controls on sibling routes: cross-office `GET /api/instructor/spectate/ofletcher` → 404, cross-office `DELETE /api/instructor/students/2` → 404.

## Impact

An instructor at one office can destroy the curriculum of another office and, with it, every cadet's graded submission records for that scenario across all offices — irreversible loss of other classes' assessment data (submissions, auto-grade results, instructor feedback). Demonstrated live: a cross-office instructor deleted another office's scenario and its submission vanished.

## Counterevidence

Strongest case against severity: scenarios are deliberately global — every student of every office drills on every scenario (`ScenarioService::getScenariosForStudent` at ScenarioService.php:16-46 has no office filter, and the seeder stamps `created_by => 'instructor'` on shared curriculum), so any instructor deleting any scenario could be argued as intended admin-like behavior. That would make this a product decision rather than a broken control. Counter: the codebase consistently treats office_id as the isolation boundary for every other instructor power (studentsApi, approve, reject, destroy, impersonate, spectate, grade, broadcast, reset — all office-scoped, verified live cross-office 404s), so scenario deletion is the sole unscoped mutation, and it silently destroys other offices' students' graded submissions, which no shared-curriculum design would intend. Instructor accounts are also not mutually trusted where it matters (the model isolates their cohorts). Rated low accordingly: real issue, limited blast radius.

## What Would Change This Severity

Evidence that scenarios are intended to be office-private (per-office curriculum) would raise this to medium/high; conversely, a product statement that all instructors are trusted co-admins of a single global curriculum would reduce it to informational hardening.

## Technical Analysis

`DashboardController::deleteScenario` (:445-475) checks only `$user->role !== 'instructor'` and then calls `ScenarioService::deleteScenario($id)` (ScenarioService.php:285-296), which loads the scenario by primary key, deletes **all** `Submission` rows for that scenario id, and deletes the scenario — no `created_by` comparison and no office check (the Scenario model has no office column at all). Every sibling instructor operation enforces the office boundary by resolving the target through `where('office_id', $user->office_id)` (approve :257, reject :287, destroy :316, impersonate :353, spectate DashboardController:380-382, grade :487-491), making scenario deletion the sole cross-office mutation. The submission cascade means the integrity impact extends beyond the scenario object to students' graded coursework that the deleting instructor has no relationship to.

## Proof of Concept

1. As instructor A (office LON1A0980), create a scenario via POST /api/instructor/scenarios (201).
2. Have a cadet submit against it via POST /api/dashboard/scenarios/{id}/submit (200).
3. As a cadet, attempt DELETE /api/instructor/scenarios/{id}: rejected 403 (role gate works).
4. As instructor B of a DIFFERENT office, issue DELETE /api/instructor/scenarios/{id}: returns 200 and the scenario is deleted.
5. Query the submissions table for that scenario id: zero rows remain — other-office students' graded work was destroyed by a foreign-office instructor.

```python
# instructor B session (office XOFF22); scenario created by instructor A (office LON1A0980)
scenario_id = "zz-xcheck-3523"

r = s.delete(f"http://127.0.0.1:8088/api/instructor/scenarios/{scenario_id}",
             headers={"X-XSRF-TOKEN": xsrf_token, "Accept": "application/json"})
print(r.status_code, r.json())
# -> 200 {'success': True, 'message': "Scenario 'zz-xcheck-3523' deleted successfully."}
# submissions WHERE scenario_id = 'zz-xcheck-3523' now: 0 rows
```

## Code Analysis

**Location 1:** `app/Http/Controllers/DashboardController.php` (line 456)

```diff
-         $deleted = $this->scenarios->deleteScenario($id);
+         $scenario = Scenario::find($id);
+         abort_unless(
+             $scenario !== null
+             && $scenario->created_by !== null
```

## Remediation

Resolve the scenario before deleting and reject with 404 unless the current instructor is the creator (or the row is shared seeded curriculum). Longer term, add an office dimension to scenarios so instructor listings and management can be scoped consistently with every other instructor operation.

## Fix Verification

Security closure: re-traced the patched controller — a non-creator instructor now fails `abort_unless` with 404 before ScenarioService::deleteScenario runs, so neither the scenario row nor the cascading Submission delete can execute for that caller; the creator path and the seeded-curriculum path are unchanged. Bypass review: sibling mutation routes checked — approve/reject/destroy/impersonate resolve the student with `where('office_id', $user->office_id)` (verified live: cross-office 404), gradeSubmissionApi checks submission user office, broadcast/reset take the office from the authenticated user, so no equivalent unscoped deletion remains. Preserved behavior: creator deletes own scenarios; seeded scenarios (`created_by = 'instructor'` from the seeder) remain manageable by any instructor, preserving shared-curriculum workflows; 404 (not 403) keeps scenario ids non-enumerable. Repository checks: code-trace only on the shared runtime (no restart/test run to avoid disrupting concurrent agents); hunk uses existing `abort_unless` style from the same controller; gate 5 flagged for reviewer to run `php artisan test --filter=Scenario`.

## Assumptions

Attacker holds any instructor account. All instructor-object routes except scenario management are office-scoped, so the deployment model is multi-office with boundary enforcement expected between offices.
