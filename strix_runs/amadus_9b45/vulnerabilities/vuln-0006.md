# Cross-cadet PNR disclosure via unscoped single-letter PNR index (RT/A) and list-line retrieval

**ID:** vuln-0006
**Severity:** MEDIUM
**Found:** 2026-11-08 16:53:26 UTC
**Target:** http://127.0.0.1:8088
**Endpoint:** /api/terminal/execute
**Method:** POST
**CWE:** CWE-639
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Trivial

## Description

The terminal's single-letter PNR index (`RT/A` … `RT/Z`) queries the 50 most recently updated PNRs with no user or office scoping, so any authenticated cadet receives the passenger names and record locators of classmates' bookings, and the follow-up `RT<LINE>` command returns the complete foreign PNR without any ownership check.

## Evidence

Exchange 211 (cadet B `RT/S`) returned index lines `1 SAMPLE/ENTRY MR HHJLSJ 15NOV LON1A0980` and `2 SAMPLE/ENTRY MR BXU79M …` — both PNRs stored by cadet A — plus `lastPnrList` containing the full records with contacts (`AP LON 44-20-7123-4567-A`). Exchange 212 (cadet B `RT2`) returned the complete foreign PNR display (`1.1.SAMPLE/ENTRY MR`, segment `BA 745 Y 15NOV LHRJFK`, contact, ticketing, received-from) with `commandType: RT_LINE`. Control exchange 292: the same cadet's direct `RT<locator>` was rejected `ACCESS RESTRICTED: PNR BELONGS TO ANOTHER USER`, proving the ownership check exists but is bypassed by the index path.

## Impact

Any approved cadet reads the full training PNRs of every other cadet in the database (and instructors' records): passenger names, itineraries, contact phone/email elements, ticketing arrangement, received-from values, and form of payment via the full-record response. This defeats the per-user PNR isolation the direct RT<locator> path enforces, and exposes other students' practice work product to copying.

## Counterevidence

Considered design intent: instructors legitimately need cross-student visibility, and the sibling surname branch already scopes students, so scoping here matches existing intent rather than fighting it. Considered impact limits: data is simulated training data, and the direct RT<locator> path correctly blocks authenticated cadets — the leak requires the two-step index+line-retrieve, both verified working. Checked whether the instructor exemption could still leak cross-office student data to an out-of-office instructor: yes (query stays unscoped for instructors), noted in the report as residual hardening; within the product's instructor-trust model this is accepted. Verified the display does not include FOP/TST lines in the index output itself, but the full record including FOP is returned by the RT<LINE> step and in updatedState.

## What Would Change This Severity

Presence of real (non-simulated) personal contact data in cadet PNRs, or instructor records containing institutional content, would raise impact; restricting instructor visibility to their own office would close the residual cross-office exposure.

## Technical Analysis

In `AmadeusParser.php`, the RT retrieval family handles `RT/<X>` searches. The surname branch (>=2 chars) correctly scopes the query: `Pnr::orderBy(...)` plus `->where('user_id', $userId)` unless the caller is an instructor (:2288-2291). The single-letter "alphabetical index" branch immediately above (:2237-2240) executes `Pnr::orderBy('updated_at','desc')->limit(50)->get()` with **no scoping for any role**, then matches surnames by prefix and stores the raw `data_json` records into `$state['lastPnrList']`, returning them to the client in `updatedState`. The list-line retrieval `RT<LINE>` (:2195-2201) then copies any entry of `lastPnrList` into `activePnr` and formats it with no ownership check. The direct locator path enforces ownership (:2354), so the index branch plus line retrieval is a complete bypass of that control for authenticated cadets.

## Proof of Concept

1. As cadet A, build and store a PNR through the terminal (AN…, SS…, NM…, AP…, TKOK, RF, ET) and note the record locator.
2. As cadet B (separate session), POST /api/terminal/execute with command `RT/S` (first letter of the passenger surname).
3. The response lists cadet A's PNR(s) with passenger name and record locator — records B does not own.
4. POST again with command `RT1` (or the matching line number): the complete foreign PNR is displayed and returned in `updatedState.activePnr`, including contacts and ticketing data, with no ownership error.
5. Control: as cadet B, POST `RT<locator>` directly — rejected with `ACCESS RESTRICTED: PNR BELONGS TO ANOTHER USER`, demonstrating the ownership control exists but the index path bypasses it.

```python
# cadet B session (logged in cookie jar), after cadet A stored PNR with surname SAMPLE
def run(session_headers, cmd, state=None):
    payload = {"command": cmd}
    if state is not None:
        payload["state"] = state
    r = s.post("http://127.0.0.1:8088/api/terminal/execute",
               json=payload, headers=session_headers)
    return r.json()

res = run(hdrs, "RT/S")            # index leak: A's locators listed for B
print(res["outputLines"])
st = res["updatedState"]
res2 = run(hdrs, "RT2", st)        # full foreign PNR from leaked list
print(res2["outputLines"])         # includes AP contact line and ticketing
```

## Remediation

Apply the same caller scoping the surname-search branch already uses to the single-letter index branch: restrict the query to `user_id = $userId` for non-instructor callers (and additionally to the instructor's office for instructor callers if cross-office visibility is not intended). Also enforce ownership on the list-line retrieval paths (`RT<LINE>`, `LM/LP<LINE>`) by filtering `lastPnrList` to records the caller may read before display.

## Fix Verification

Security closure: re-traced the patched branch — the query now carries `where('user_id', $userId)` for every non-instructor caller, so a student's `lastPnrList` can only ever contain their own records; the follow-up `RT<LINE>` command can only surface entries from that list, so the cross-cadet read chain is closed end-to-end. Bypass review: checked the other list builders — `LM/LP` multi-list and `LPO` office-search return hardcoded demo PNRs, not database rows, so they cannot leak real records; the surname branch is already scoped; direct `RT<locator>` is separately guarded. Preserved behavior: instructors keep the unscoped index (classroom visibility is an instructor feature used by the dashboard spectate flows); students still see their own index results, and the seeded fallback demo record still renders when no matches exist. Repository checks: code-trace only on the shared runtime (no server restart / test run to avoid disrupting concurrent agents); the hunk mirrors the adjacent surname-branch style; gate 5 flagged for reviewer to run `php artisan test --filter=Parser`.

## Assumptions

Attacker is any approved cadet (or instructor outside the record owner's office). PNR data is simulated training data; contact fields are free-text and may contain personal phone/email.
