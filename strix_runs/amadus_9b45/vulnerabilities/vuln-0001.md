## Description

`composer.lock` pins `symfony/mime` **v8.1.7**, which is covered by CVE-2026-45070 (email header injection via non-token bytes in MIME parameter names). Fixed in v8.1.10 (also 5.4.55 / 6.4.49 / 7.4.22). The package is pulled in transitively by the direct dependency `laravel/framework` v13.38.0.

## Evidence

**Advisory evidence:** `CVE-2026-45070` applies to `symfony/mime` at installed version `v8.1.7`. The advisory is fixed in `8.1.10`.

**Transitive dependency:** introduced by the direct dependency `laravel/framework@v13.38.0`.

**Dependency chain:** `laravel/framework@v13.38.0 > symfony/mime@v8.1.7`

**Usage analysis:** imported by application code; affected API usage unconfirmed. Import check: symfony/mime is required by laravel/framework v13.38.0 and symfony/mailer v8.1.7 (composer.lock), so it is on the runtime autoload path. Affected-symbol check: `rg -l 'ParameterizedHeader' app/ config/ vendor/laravel/framework/src/Illuminate/` returns only symfony/mime's own files (Header/Headers.php, Header/ParameterizedHeader.php, Crypto/SMimeEncrypter.php) — no application or framework caller. Source-to-sink trace: the only mail-sending path is `POST /forgot-password` → `PasswordResetController::sendResetLink` (app/Http/Controllers/PasswordResetController.php:46) → `User::sendPasswordResetNotification` → Laravel `Illuminate\Notifications/MailChannel`, which constructs Symfony Email headers with fixed names (no attacker-controlled parameter names). Additionally the default mailer is `log` (config/mail.php:17, MAIL_MAILER=log in .env/.env.example), so in the default deployment mail is written to logs, not SMTP. No source reaches the vulnerable sink. This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

In the abstract, a caller that derives a MIME parameter name from untrusted input could inject CRLF/additional headers into outgoing mail. In this codebase no such caller exists: Laravel's mail layer never derives parameter names from request input, and the app's only notification is the password-reset mail, so the vulnerable path is not reachable.

## Contextual CVSS

symfony/mime is imported transitively by laravel/framework v13.38.0 (composer.lock) and loaded through Illuminate/Mail/Notifications when mail is sent, but the vulnerable API is `Symfony\Component\Mime\Header\ParameterizedHeader` with a parameter NAME derived from untrusted input. Searches across `app/`, `config/`, and `vendor/laravel/framework/src/Illuminate/Mail/` found zero references to ParameterizedHeader; Laravel sets MIME header names statically (Content-Type, Content-Disposition) and only values are user-influenced. The application's only mail send is the password-reset notification (`app/Http/Controllers/PasswordResetController.php:46` → `User::sendPasswordResetNotification`), and the default mailer is `log` (`config/mail.php:17`, `MAIL_MAILER=log`), so no MIME message leaves the host in the default deployment. No entry point reaches the vulnerable parameter-name path, so contextual impact is N/N/N; attack metrics kept from the published vector with AC:H reflecting the attacker-controlled parameter-name precondition that does not exist here.

## Remediation

Upgrade laravel/framework to a release whose constraint resolves symfony/mime >= 8.1.10 (or add a composer conflict/require for `symfony/mime:>=8.1.10` and run `composer update symfony/mime`). No application code change is required; the vulnerable parameter-name path is unused.
