# Unauthenticated PNR disclosure via guest-exempt ownership check in terminal RT retrieval

**ID:** vuln-0005
**Severity:** MEDIUM
**Found:** 2026-11-08 16:52:21 UTC
**Target:** http://127.0.0.1:8088
**Endpoint:** /api/terminal/execute
**Method:** POST
**CWE:** CWE-862
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

Unauthenticated callers of the terminal API can retrieve any stored PNR by its 6-character record locator or by a passenger-surname search, bypassing the ownership check that applies to authenticated students. The check at AmadeusParser.php:2354 only rejects when the caller is a non-owner AND is not a guest, so the no-session case reads every record.

## Evidence

Exchange 296 (unauthenticated POST /api/terminal/execute, command `RTHHJLSJ` → 200 RT_LOCATOR) returned the stored PNR of an approved cadet — name line `1.1.SAMPLE/ENTRY MR`, contact `AP LON 44-20-7123-4567-A`, itinerary `BA 745 Y 15NOV LHRJFK` — versus exchange 292, the identical command from a second authenticated cadet rejected with `ACCESS RESTRICTED: PNR BELONGS TO ANOTHER USER` (RT_UNAUTHORIZED). Guest surname search `RT/SAMPLE` likewise returned the cadet's stored record (locator list + auto-retrieve). Guest-written foreign-office queue rows verified in the database after `QE/XOFF22/9C0` from a guest session.

## Impact

Anyone who can reach the app without credentials reads the full booking record of any cadet or instructor in the database: passenger names, itinerary segments, stored contact details (phone/email as entered), ticketing data and form of payment. The same guest identity can write queue items attributed to any office id. Cross-office confidentiality boundary of the classroom is void for this data type.

## Counterevidence

Actively looked for guards that could stop this: (1) route middleware — none on the API terminal route; auth is optional by design for guest demos; (2) CSRF — verified live that the unauthenticated POST succeeds, so CSRF is not an effective control here; (3) guest restrictions elsewhere — ET, TTP, QS/QT/QD all reject guests, confirming the platform intends guests to have no data access; the RT path is the outlier, so the guest exemption looks accidental rather than a deliberate share-everything policy; (4) data sensitivity — booking data is simulated, but contact fields are free-text trainee input and the endpoint equally exposes instructor-stored PNRs. Only real constraint found: attacker must guess/know a 6-char locator or surname; low entropy in a classroom pool.

## What Would Change This Severity

Confirmation that deployments place real (non-simulated) passenger contact data into PNR contact fields, or that instructor-created reference PNRs carry institutional data, would raise confidentiality impact; a WAF or gateway enforcing auth in front of /api/terminal/execute would lower it.

## Technical Analysis

`routes/web.php` registers `POST /api/terminal/execute` outside any auth middleware, and `TerminalController::execute` maps a missing session to `$userId = 'guest'` (TerminalController.php:72). In the parser, the direct-locator retrieval branch loads any stored PNR with `Pnr::find($arg)` and applies the ownership check `! $isInstructor && $dbPnr->user_id !== $userId && $userId !== 'guest'` (AmadeusParser.php:2352-2356): the third clause makes the check false for every unauthenticated caller, so guests receive the full formatted PNR. The surname-search branch applies the same guest exemption to its user scoping (`if (! $isInstructor && $userId !== 'guest')` at :2288-2291), letting guests list and auto-retrieve foreign records by surname. Finally the queue branch `QE/<office>/...` (:2457-2464) creates a QueueItem attributed to an arbitrary office with no guest check at all. Other persistence branches (ET :1881, TTP :2383, QS/QT/QD :2433/:2512) explicitly reject guests, showing the guest exemptions on RT paths are the outlier rather than a deliberate policy.

## Proof of Concept

1. Store a PNR as an approved cadet via the terminal (availability, sell segment, name, contact, ticketing, RF, then ET) and note the returned 6-character record locator.
2. Start a fresh HTTP session with no login cookies (only the CSRF bootstrap from GET /login).
3. POST /api/terminal/execute with command `RT<locator>`.
4. The response returns the complete stored PNR (passenger names, segments, contact phone/email, ticketing, received-from).
5. As a control, send the same command authenticated as a different cadet and observe it rejected with `ACCESS RESTRICTED: PNR BELONGS TO ANOTHER USER`.
6. Repeat with `RT/<surname>` from the anonymous session: the unscoped surname search returns a locator list of every matching stored PNR and auto-displays the record when exactly one matches.
7. From the same anonymous session, POST command `QE/<ANY-OFFICE>/9C0` with state containing the chosen office id: the response confirms a queue item was created for that foreign office (row verified in the database).

```python

BASE = "http://127.0.0.1:8088"

s = requests.Session()  # never logs in
s.get(BASE + "/login")
hdr = {"X-XSRF-TOKEN": urllib.parse.unquote(s.cookies.get("XSRF-TOKEN", "")),
       "Accept": "application/json"}

def run(cmd, state=None):
    payload = {"command": cmd}
    if state is not None:
        payload["state"] = state
    r = s.post(BASE + "/api/terminal/execute", json=payload, headers=hdr)
    return r.json()

# PNR record locator previously stored by an authenticated cadet
print(run("RTHHJLSJ")["outputLines"])        # full foreign PNR, no session
print(run("RT/SAMPLE")["outputLines"])       # surname search: list + auto-retrieve
# unauthenticated queue write to a foreign office
print(run("QE/XOFF22/9C0", {"officeId": "XOFF22",
      "activePnr": {"recordLocator": "ZZZ9Y8",
                    "passengers": [{"id": "1.1", "lastName": "GUESTWRITE",
                                    "firstName": "TEST", "title": "MR", "type": "ADT"}],
                    "segments": []}})["outputLines"])
```

## Remediation

Require an authenticated session for terminal command execution (return 401 for guests in TerminalController::execute, matching the ET/TTP/queue branches that already refuse guests), and delete the `$userId !== 'guest'` exemption from the RT ownership check and from the surname-search scoping so no caller identity other than a same-office instructor can read stored PNRs they do not own. Reject or office-scope guest queue writes on the QE office-target path.

## Fix Verification

Security closure: re-traced the patched paths — the 401 in TerminalController::execute fires for every unauthenticated request before the parser is invoked, so no guest branch is reachable via HTTP anymore; even if a guest path were re-introduced, the RT locator branch now returns RT_UNAUTHENTICATED before the retrieved record is used, and surname search applies `where('user_id', $userId)` for all non-instructors. Bypass review: checked sibling retrieval branches — `RT0` list replay and `RT<LINE>` reuse data already held in client state and cannot disclose new records without first obtaining them through RT search/locator, both now gated; instructor exemption retained deliberately (matches the office-scope model used elsewhere). Preserved behavior: guest sessions previously could run availability/decode/help commands; the controller 401 now blocks all guest usage — intentional, documented in the PR body; if product wants anonymous demos, scope the 401 to data-touching commands (RT, ET, TTP, Q). Repository checks: gates 1-3 are code-trace only (shared runtime used concurrently by other agents; did not restart the server or run the test suite) — hunk syntax checked against surrounding code style; gate 5 (tests) not executed, flagged as a gap for the reviewer to run `php artisan test`.

## Assumptions

Deployed instance exposes /api/terminal/execute without authentication, as in this checkout. Training PNRs contain practice passenger data; contact fields may hold real phone/email entries typed by trainees.
